# MARD 色库体系对齐现实方案设计

**日期：** 2026-04-25  
**状态：** 待评审

## 背景

当前产品在 MARD 色库上混用了三类概念：

1. 现实世界的官方方案
2. 系统内部的算法减色档位
3. 用户自定义的个人颜色库存

现状里，这三类概念在 UI 和帮助文案中没有清晰分层，容易让用户误以为 `48 / 72 / 96 / 150 / 200` 这类档位也是现实世界的 MARD 官方方案。这个表达与现实世界主流认知不一致。

结合当前代码和已确认的产品方向，本次设计目标是把 MARD 体系收敛为“官方方案 + 我的颜色 + 算法控制项”三层结构，避免系统自行发明“官方方案”。

## 目标

本次改造的目标是：

- 系统官方方案只保留现实世界主流口径
- 用户个性化需求统一通过“我的颜色”处理
- 算法减色能力继续保留，但不再伪装成官方方案
- 帮助页、引导页、编辑页文案全部和新的产品口径一致
- 不破坏现有编辑、减色、云保存、用户颜色同步功能

## 非目标

本次不处理以下事项：

- 不扩展新的品牌色库
- 不新增新的豆子品牌切换 UI
- 不重写整套配色算法
- 不调整“我的颜色”云同步协议
- 不在本次内强行引入更多现实世界 MARD 商业 SKU 展示

## 现实世界口径

本次系统口径统一为：

- `MARD 221 常用色`
- `MARD 291 全色`

系统不再把 `48 / 72 / 96 / 150 / 200` 称为“系统色系方案”或让用户误解为“官方配色方案”。这些能力如果继续保留，只能以算法调节项的身份存在。

## 产品结构设计

### 1. 官方色库层

编辑页中的系统官方选项改成：

- `MARD 221 常用色`
- `MARD 291 全色`

这两个选项属于“官方色库选择”，表达的是基础色库范围，而不是算法减色结果。

### 2. 用户色库层

保留现有“我的颜色”能力，作为独立于官方方案的第二层：

- 用户可以自行管理拥有的颜色
- 启用后，生成图案时优先只在“我的颜色”范围内匹配
- 如果用户未配置“我的颜色”，则走官方色库

系统应明确告诉用户：

- “我的颜色”是个人库存，不是官方色系方案

### 3. 算法控制层

现有 `48 / 72 / 96 / 150 / 200` 不再作为“官方方案”展示，而改成算法控制项，例如：

- `颜色精简`
- `颜色数量限制`
- `精简强度`

这层表达的含义是：

- 在已经选定的基础色库范围内，再通过算法控制最终使用的颜色数量

也就是说，最终生成逻辑变成：

`官方色库 / 我的颜色` -> `算法精简控制` -> `最终图案色数`

## 编辑页交互设计

编辑页的色库相关交互重新拆成两个区块：

### 区块 A：基础色库

- `MARD 221 常用色`
- `MARD 291 全色`
- `我的颜色`

三者是互斥的基础色库来源。

推荐默认值：

- 默认选择 `MARD 291 全色`

### 区块 B：颜色精简

把原来的 `48 / 72 / 96 / 150 / 200 / 291` 改造成算法控制项：

- 文案不再叫“系统色系”或“当前 XX 色方案”
- 改成如：
  - `不精简`
  - `轻度精简`
  - `适中精简`
  - `重度精简`
- 或继续保留数值，但语义改成：
  - `最多 48 色`
  - `最多 72 色`
  - `最多 96 色`
  - `最多 150 色`
  - `最多 200 色`
  - `不限制`

推荐实现采用第二种，即保留数字但改成“上限”语义。原因是：

- 用户更容易理解实际效果
- 你们现有算法和状态结构改动最小
- 不会丢掉现有能力

## 帮助文案与引导文案设计

需要同步改的内容包括：

- 首页或帮助页中的“当前支持哪个拼豆色系”
- 引导页里的“MARD 拼豆色板”说明
- 编辑页色系弹层的标题和说明

统一文案原则：

- 现实世界方案叫“官方色库”
- 用户库存叫“我的颜色”
- 算法分档叫“颜色精简”或“颜色数量限制”

避免再出现这些混淆表达：

- “当前支持 MARD 色系，可调整颜色数量”  
  这句话需要拆成“当前支持 MARD 官方色库；可进一步限制颜色数量”

## 数据与代码结构设计

### 1. 色库数据层

在 `beadColors.ts` 中，把当前“全系统只用 MARD 291”改造为更明确的结构：

- 保留 `mardColors`
- 新增 `mard221Colors`
- 新增基础色库选项定义
- 保留算法数量限制选项，但改名为“颜色精简上限选项”

### 2. 用户颜色服务层

`myColorsService.ts` 继续保留现状，不改变云同步协议。

### 3. 编辑页状态层

编辑页需要把当前单一的 `colorCount` 语义拆清楚：

- 基础色库来源
- 颜色数量上限

避免后续再出现“一个字段既表示官方方案，又表示算法档位”的语义混乱。

### 4. 图像分析推荐层

`imageAnalysisService.ts` 现在直接返回 `48 / 72 / 96 / 150 / 200 / 291` 这一类推荐数量。  
本次需要把它的语义改成：

- 推荐颜色数量上限

而不是推荐“官方方案”。

## 兼容策略

现有本地草稿、会话数据、历史项目里可能已经存有旧的 `colorCount` 值。  
本次需要兼容：

- 历史项目继续能正常打开
- 打开后，旧值按“颜色数量上限”解释
- 如果缺少新的基础色库字段，则回退到 `MARD 291 全色`

## 错误处理

需要考虑这些边界情况：

- 用户启用“我的颜色”但一色未选
  - 应拦截并提示先配置颜色，或者回退官方色库
- 用户选择 `MARD 221`，但精简上限大于 221
  - UI 可展示，但最终实际上限不能超过基础色库大小
- 用户选择“我的颜色”，个人库存少于当前上限
  - 最终以上传/匹配时实际可用色数为准

## 测试设计

本次至少覆盖：

1. 数据层测试
- `MARD 221` 真实颜色数正确
- `MARD 291` 真实颜色数正确
- 精简上限选项语义正确

2. 业务层测试
- 基础色库切换后，实际使用的候选色集正确
- 启用“我的颜色”后，颜色池切换正确
- 历史项目兼容正确

3. 页面层测试
- 编辑页文案正确
- 帮助页文案正确
- 引导页文案正确

## 推荐实现顺序

1. 先收敛色库数据结构
2. 再收敛编辑页状态语义
3. 再替换帮助页和引导页文案
4. 最后补兼容和测试

## 风险

主要风险有两类：

1. 旧数据兼容
- 如果旧项目直接把 `291` 理解成“官方方案”，迁移时必须仍能工作

2. 221 色清单准确性
- 需要以你们最终认可的现实世界 MARD 221 口径为准
- 如果仓库当前只有 291 色全集，221 子集需要明确选取规则并固化

## 验收标准

完成后应满足：

- 系统里不再把算法档位误导成 MARD 官方方案
- 用户可以明确区分：
  - 官方色库
  - 我的颜色
  - 颜色精简
- 编辑器生成逻辑仍可用
- 历史项目不会打不开
- 帮助页和引导页的表达与现实世界口径一致
