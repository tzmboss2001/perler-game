# 社区功能技术路线（抖音小程序版）

日期：2026-03-02  
范围：`perler-beads` + `perler-beads-server`

## 1. 目标与原则
- 目标：社区发布稳定、可审核、可追溯、可扩展，移动端体验优先。
- 原则：
  1. 发布数据与渲染数据解耦（保存“可回放快照”）。
  2. 缩略图与详情图分层（列表快、详情准）。
  3. 审核与展示解耦（审核状态驱动可见性）。
  4. 向后兼容优先（历史作品不因色系迭代失真）。

## 2. 当前现状（基于代码）
- 已有：发布、社区列表、详情、点赞、制作次数。
- 已有：缩略图自动修复与部分兼容补偿。
- 已有：`review_status` 字段与基础审核接口骨架。
- 风险：
  1. 详情渲染仍受历史调色板差异影响。
  2. 审核流程未完全产品化（权限、后台页、操作日志）。
  3. 社区治理策略（举报、风控、下架）仍是基础态。

## 3. 分阶段路线

### Phase A：数据与审核基础（先完成）
- A1. 数据层
  - 社区作品保存：`bead_data` + `palette_brand/version/name` + `thumbnail_url`。
  - 增加审核状态字段：待审/通过/驳回/下架（已落库模型）。
- A2. 接口层
  - 审核列表接口（按状态分页）。
  - 审核动作接口（approve/reject/hide/restore）。
- A3. 展示规则
  - 用户侧只看到 `status=1 && review_status=1`。
  - 管理侧可看全量并执行审核动作。
- 验收
  - 服务端 `go build` 通过。
  - 审核动作能改状态并影响前台可见性。

### Phase B：渲染一致性（核心）
- B1. 发布时生成两份渲染产物
  - 列表缩略图：轻量 PNG。
  - 详情预览图：标准分辨率 PNG（与制作页视觉一致）。
- B2. 详情展示优先级
  - 优先详情预览图 > 回放 bead_data 渲染 > 历史兼容兜底。
- B3. 历史作品修复
  - 后台任务按批重建详情图与缩略图。
- 验收
  - 同一作品在制作页/社区详情视觉差异可控（色差最小化）。

### Phase C：社区产品化
- C1. 分类体系
  - 系统标签（动物/花卉/动漫等）+ 用户自定义标签。
  - 排序：最新、最热、制作数。
- C2. 互动治理
  - 举报、下架原因、违规词检测、频率限制。
- C3. 推荐与运营
  - 精选位、活动位、榜单位。

### Phase D：上线与运维
- D1. 观测
  - 发布成功率、图片生成失败率、审核时延。
- D2. 数据
  - 社区核心表索引与归档策略。
- D3. 安全
  - 鉴权、限流、审计日志。

## 4. 本周执行顺序（建议）
1. 完成 Phase A 的管理端闭环（接口 + 页面 + 权限）。
2. 完成 Phase B 的“详情标准图”链路（发布即生成）。
3. 跑历史回填脚本，修复老作品。
4. 补齐监控与告警后，再进入抖音提审。
